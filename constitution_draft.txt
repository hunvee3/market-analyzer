/speckit.constitution We are building a PWA application that allows users to create and manage grocery lists and create purchases of those lists at the super market, where they will be able to load products to a list by product. The objective of the app is, appart from allowing users to manage grocery lists and purchases,  to track down product prices, purchases expenses and compare both product prices and purchases with other instances to allow users to evaluate theri expenses and choose better markets to buy from. 

For this project this is our constitution:

1- Architecture
Both front end and Backend will follow Hexagonal Architecture to the letter. This mean that both front and back will have each feature separated by layer (domain, application and infrastructure). NO Exception. Both will have usecases even if these only call ports implementation. We want the whole architecture there even if it is too much boilerplate.

2- Testing and Development(NON-NEGOTIABLE)
TDD mandatory: Test first->failing->implements-> re test-> pass
All unit test need to be truely a unit test, meaning all external dependencies MUST be mocked.
Test must follow the AAA principle and descriptions should be of Given/When/Then format.
Use libraries when needed but require approval first. No library should be used if the implementation is simple enough that it can be done in the project without raising too much the complexity.

3- Error handling and Observability
API errors must comply the following response:
{
    statusCode: HttpStatus,
    errorCode: string,
    message:string
}

In special cases like validation errors the structure should be:

{
    statusCode: HttpStatus,
    errorCode: ValidationError,
    message:string,
    details:{
        issues: ValidationIssue[]
    }
}

where ValidationIssue is:
{
    field:string,
    rules: ValidationRule[]
}

where ValidationRule is:
{
    rule:string,
    message:string,
    params?: Record<string, any>
}

For example:
{
    statusCode: 400,
    errorCode: ValidationError,
    message: "Could not create the resource due to field valdiation failure",
    details: [
        {
            field:"user_name",
            rules:[
                {
                    rule: "minLength",
                    params:{ length: 8}
                }
            ]
        }
    ]
}

All errors must be logged, but sensible data must be hidden.

3- FrontEnd Tech Stack
Front end must be developed using React and Typescript.
Dates formats and timezones should be hnadled by date-fns if necessary
The UI should be done using MUI library with styled components
Styles longer than 3 properties should be handled in a sepearte styles file per component. Less than 3 props can be handled inline.
Components that only are Styles should not be tested (mandatory).

All other components should be tested using react testing library.

If no backend is present when creating a frontend feature, make sure to create a mock for the api so that we can realistically test.

Project must follow best practices in frontend, accesibility and UX. Linting rules are required for react and react hooks.

4- Backend
Backend must be implemented using Fastify and Typescript.
all responses, unless specified other way, should return JSON data.
Apis should be RESTful.

Postgres databases should be used for storage.

ORM should be Lucid, a feature-rich ORM inspired by Laravel's Eloquent.

5- Branching strategy

The projects must follow git flow strategy.

Epics should create a new branch from develop and all related features should branch put and be merged into the epic branch.

If no epic then feature branches should branch out from develop and back to it.

## Governance
- Constitution supersedes all other practices
- Amendments require documentation in PRs with ratification date
- All PRs must verify compliance with principles
- Use GUIDANCE.md for runtime development decisions
- Violations block merges until resolved
